# Anthropic：エージェント記憶を構成する四つの層

- セッションをまたぐ記憶を、原ログ、記憶ノート、構造化したwiki、次回に注入する小さな文脈の四層で整理する。
- オフラインの「dreaming」は外部記憶を修正・整理する工程であり、モデル重みの更新とは異なる。
- 検索とwikiの併用には改善例があるが、作成費用、古い記憶、上書きによる情報欠落などの負担も示される。

## 実務向けの読み方（7行）

- まず原ログを残し、記憶ノートの誤りを元の証拠まで戻って修正できるようにする。
- ノートは将来の有用性を予測して書くため、必要な情報を落とすことがある。
- wikiは文書横断の整理に役立つ場合があり、単一ファイル検索には明確な利点がない例もある。
- 毎回の注入文脈は小さくし、詳細は検索で取り出す設計を比較する。
- 正解率だけでなく、記憶の作成・保守・検索・回答の費用を分けて測る。
- 複数の書き手による上書きや、古い事実の残存も評価対象に含める。
- 以下の確認案は未実施であり、紹介された製品機能や性能を独立に検証したものではない。

## 問いと構成

エージェントは何を保存し、どう整理し、次回の作業で何を読むべきか。記事は、原ログ・エージェントが書いたノート・リンク付きwikiなどの構造化表現・小さな注入文脈を区別する。各層は別々の目的を持ち、すべてを一つの要約に置き換える構成ではない。

dreamingは待機時などの計算でログとノートを照合し、誤りの訂正、統合・削除、wiki作成、小さな索引への昇格を行う。ここで変わるのは外部ファイルである。生物学的な睡眠と同じ仕組みを示したものでも、モデルの重みを学習したものでもない。

## 報告結果と根拠

### データベース課題とノート

CL-Bench 1.0のデータベース課題では、各問題を新しいセッションで解き、記憶ディレクトリだけを引き継ぐ。回答後には正解の解法が渡される。Opus 5は記憶なし0.564から記憶あり0.828、Opus 5.5は0.655から0.838、Sonnet 5.5は0.644から0.833へ改善した。

Sonnet 4.6は0.330から0.364だったが、ノートを読み仮説を試すよう指示すると0.641となった。記憶を渡すだけで同じ効果が出るとは限らない。失敗だけを記録する条件では利益が減った。これらは当該課題とフィードバック条件の結果であり、CL-Bench全体への一般化ではない。

### 原ログからの修正とゲーム事例

Pokémon Redでは、原ログを照合して誤った場所の記憶を修正する事例を示す。Sonnet 3.7とFable 5の約1万ステップの比較は各1回で、前者は413ファイル・225フォルダでバッジ1個、後者は合計10ファイル・2フォルダとグローバル記憶で4個だった。モデルも変わるため、ファイル数を減らしたことが改善の原因とは言えない。

### wikiと検索

非公開のStainless社内資料（約35万ファイル、4.2億トークン）、25問の評価では、dreamingを2から128セッションへ増やすとwiki単独の評価基準充足率が13%から48%になった。wiki＋検索は54%から61%、検索単独は53%。ここでの割合は評価基準の充足率であり、問題正解率と同一ではない。

wiki利用で回答時に約2万トークンを節約したと報告するが、wikiの準備・維持費は別である。dreamingの計算量を増やしているため、総費用の削減が示されたとは扱わない。非公開コーパスなので同じ条件の外部再現は難しい。

Harveyの法務課題では、文書横断の推論に改善例がある一方、単一文書の検索には明確な改善がない例もある。ある合併契約の事例では、元の10文書115KBに対しwikiが68ページ203KBとなり、要約しても小さくならなかった。並行する書き手による上書きで条項が欠落し、57基準中41（72%）を満たした。契約ごとの担当と正確な条項の別ページ保存など、課題に合わせて指示を変えると57基準すべてを満たせる例になった。単一事例の修正であり、一般的な完全性保証ではない。

## 限界

企業内の異なるモデル・課題・指示による実験と事例をまとめた記事であり、共通条件の包括的比較ではない。全条件の反復数・信頼区間・費用が揃っているわけではなく、記憶が長いほど、また構造化が複雑なほど良いとも結論できない。

誤ったノートは次回に持ち越され、情報を省いたwikiは原資料の代替として不完全になる。更新頻度、陳腐化、注入しても読まれない記憶、リンク修復、書き手間の整合性、維持費用が設計上の課題となる。

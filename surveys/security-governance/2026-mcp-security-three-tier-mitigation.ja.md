# MCPのセキュリティ対策をサーバー・ゲートウェイ・プロトコルで分担する

## 概要

- **何についてのものか**：MCPのセキュリティ対策を、実際に制御できる3つの層へ割り当てる枠組みを示したプレプリント。
- **何を述べているか**：表1ではOWASP MCP Top 10の主担当を、サーバー5件、ゲートウェイ2件、プロトコル3件とした。
- **留意点**：確信度は、Go製の管理ファイル転送サーバー1件の事例を踏まえた定性的な判定。

## 実務向け6行

- 著者らは4つの質問で、どこが対策を強制でき、何がその判定を支えるかを整理する。
- 本人確認や権限の管理は、サーバーで強制できる対策として扱う。
- ゲートウェイは接続先をまたぐポリシーを強制し、運用記録を集約できる。
- 外部データと指示が同じモデル文脈に入る場合に、プロトコル設計上の限界が残ると論じる。
- 検証はGo製の管理ファイル転送サーバー1件で、高・中・低は対策の失敗率を実測した値ではない。
- 応用案は、各層の担当と、承認や権限を確認できない場合の扱いを記録すること。

## 書誌・確認範囲

Christopher Krakauer、Andreas Schaad、*Where Does MCP Security End? A Three-Tier Mitigation Mapping Framework for the OWASP MCP Top 10*。arXiv v1、2026年11月2日。2026年11月23日（JST）に第5〜7節と表1を中心に確認。独立したサーバー検証は未実施。

## 根拠と限界

- **分類。** 各項目に主担当となる層を割り当て、他の層の部分的な対策も認める。表1の確信度は高3件、中4件、低3件。低とした3件はプロトコルが主担当だった。
- **事例。** 管理ファイル転送の実装では、決定的なサーバー側の対策は想定どおりに動いたと報告されている。モデルの判断を介するリスクには他の層に課題が残った。開発に関わる観察者による評価、単一のSDKと構成、定性的な判定により、一般化には限界がある。
- **運用上の読み方。** MCPの経路選択、呼び出し元の認可、モデルによる返却内容の解釈は、それぞれ確認する。3層への割り当ては著者らがOWASPの分類に適用した分析結果。

## 応用・無料の確認案

提案。架空のファイルサービスで、利用者の確認、文書へのアクセス権、変更の承認、監査記録の担当を表にする。許可と拒否の数例を使い、どの部品がルールを強制し、認可を確認できなければどう扱うかを机上で確かめる。

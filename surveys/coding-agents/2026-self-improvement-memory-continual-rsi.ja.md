# Self-Improvement Memory：ハーネス改善の根拠を引き継ぐ

## 概要

- **何についてのものか**：ハーネス改善のための記憶を扱うプレプリント。
- **何を述べているか**：改善の根拠を残し、その後の最適化に活用する。
- **留意点**：引継ぎによる改善は保証されない。

## 実務向けの読み解き

- **問い**：ハーネスや利用モデルが変わっても、何を引き継ぐべきか。
- **方法**：SIMに原因仮説、変更、予測、実測結果、適用条件を残す。
- **結果**：対応をそろえたコーディング実験で効果を報告。数値は下記に記載。
- **開発への応用案**：Codexのハーネス変更に、仮説・コミット・検証結果を結びつける。
- **記憶への応用案**：改善台帳を、作業メモやスリープ処理の要約から分けて管理する。
- **注意点**：残した原因説明も再検証すべき仮説であり、変更を自動承認する根拠にはしない。

## 手法・証拠・限界

SIMは最適化側の記憶であり、実行モデルの重みは固定。比較は初期ハーネス、改善済みハーネスのみ、原因説明のみの記憶、完全なSIM。保留評価のフィードバックは最適化に渡さない。

Terminus-2を使ったコーディングの10組の対応比較ではSIMが9組で上回り、平均差は**2.36スコアポイント**、対応検定の**p=0.003**（表3）。他の主要条件は、条件ごとに最適化1回の報告。

各実行は10ラウンド・各5候補をそろえるが、トークン数・時間は同一ではない。選択された変更の失敗も記録し、記憶全体を検索なしでプロンプトに入れる。互換インターフェースが前提。最後の世代移行では新規最適化の方が高得点。引継ぎ記憶と移行先での更新は一体で評価されている。出典：[§§3–4・限界・付録C–D](https://arxiv.org/html/2611.18856v1)。

## Codex／GitHubへの応用案

**ここからは本ノートの設計案。未実装・未検証。** ハーネス設定の近くに、版管理する `improvement-ledger/` を置く構成から始めたい。問題には安定したIDを付け、似た表現だけで異なる説明を統合せず、競合する仮説も残す。

変更ごとに、失敗の証拠、原因仮説、期待するチェック、モデル識別子、ハーネスのコミット、評価セットの版、実測結果、置換・撤回の判断を記録する。「評価候補として選ばれた」と「採用条件を満たした」は別の状態にする。パッチを取り消した後でも、判断の経緯を読み直せることが重要。

作業中の記憶は従来の場所に置く。スリープ・整理処理では、この台帳から教訓候補を作り、変更されない証拠へリンクさせる案が考えられる。プロンプト、スキル、ツールのラッパー、完了条件へ反映する前に再検証する。既存のスリープ実装が、この動作をすでに備えるという意味ではない。

## 無料で実施できる予備確認

1. 機密情報を含まない既存PRと保存済みログを3〜5件選び、手作業で台帳を作る。新たなモデル呼出しや環境構築は行わない。
2. 別の読み手が、予測・実際の結果・対象の版・未解決の疑問を各記録から復元できるか確かめる。
3. 将来の比較案として、同じハーネスのコミットから「台帳なし／原因説明のみ／証拠付き台帳」を比較する。採用判定用の課題を編集範囲外に固定し、退行、同じ失敗の繰返し、成功率、トークン数、時間を測る。
4. まずオフラインで記録手順を確認する。後日の有償ベンチマークには別途予算が必要で、この予備確認で論文の性能差を再現したとはいえない。
